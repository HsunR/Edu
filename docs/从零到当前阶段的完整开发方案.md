# Intelli-Edu 从零到当前阶段的完整开发方案

> 本文描述的是：如果今天从一个空仓库重新建设 Intelli-Edu，如何按正确顺序开发，最终达到当前项目拥有的能力——Vue 管理端 + Spring Cloud 微服务 + 用户/课程/资源/考试/知识/学习/AI 域 + Docker 本地环境。
>
> 它是项目建设蓝图，不是对当前代码缺陷的整改清单。

## 1. 最终要建设成什么

### 1.1 产品目标

建设面向高校或培训机构的智慧教育平台，覆盖“教、学、练、考、评、辅”完整链路：

```text
教师：建课 → 建班 → 编排章节 → 上传资源 → 关联知识点 → 出题组卷 → 发布考试 → 查看学情
学生：注册登录 → 加入课程/班级 → 学习章节资源 → 完成练习/考试 → 查看成绩错题 → 获得学习建议
管理员：管理用户、角色、菜单、课程分类、资源与系统配置
AI：基于授权课程资料的问答、资料解析、辅助生成或学习辅助
```

### 1.2 最终服务清单

| 服务/模块 | 责任 | 当前对外端口 |
|---|---|---|
| `Intelli-Edu-gateway` | 统一路由、鉴权、限流、接口文档聚合 | 8890 |
| `Intelli-Edu-user` | 注册、登录、用户、角色、菜单、院系、验证码 | 8891 |
| `Intelli-Edu-resource` | 文件/视频资源元数据、上传与访问授权 | 8892 |
| `Intelli-Edu-course` | 课程、分类、班级、成员、章节、资源关联 | 8893 |
| `Intelli-Edu-exam` | 题库、题目、试卷、考试、答卷、成绩 | 8894 |
| `Intelli-Edu-Knowledge` | 知识点、知识树、题目/章节知识关联 | 8895 |
| `Intelli-Edu-learning` | 学习进度、错题、掌握度、学习推荐/统计 | 8896 |
| `Intelli-Edu-Ai` | AI 会话、课程资料处理、检索增强能力 | 8897 |
| `Intelli-Edu-api` | 跨服务 DTO、Feign 客户端和降级契约 | 内部模块 |
| `Intelli-Edu-auth` | 网关鉴权与资源服务鉴权 SDK | 内部模块 |
| `Intelli-Edu-common` | 统一响应、异常、日志、Redis、MyBatis 等公共能力 | 内部模块 |

### 1.3 最终运行环境

```text
前端 Vue 3/Vite
       │ /api
       ▼
Spring Cloud Gateway ── Nacos（注册与配置）
       │
       ├── user / course / resource / exam / knowledge / learning / ai
       │        │                 │
       ▼        ▼                 ▼
PostgreSQL      Redis         RabbitMQ
（含 pgvector） （缓存/会话）  （业务事件）
       │
对象存储、视频点播、短信邮件、LLM（可选外部能力）
```

## 2. 建设原则与顺序

1. **先完成用户可感知的纵向闭环，再增加横向技术。** 先让教师建课、学生学习；之后再做算法、AI 和复杂分布式能力。
2. **先设计数据所有权，再定义接口。** 不允许通过跨库查询“图省事”。
3. **业务服务按领域拆分，公共能力按 SDK 抽取。** 业务规则不塞进 `common`。
4. **一个阶段至少有可演示成果。** 不连续数周只做底层重构。
5. **本地环境与生产环境的运行方式保持一致。** 全部依赖容器化，机密配置通过环境变量或 Secret 注入。

建议总工期：单人 20～28 周；3～5 人团队 14～18 周。下面的周期按 2 周一个 Sprint 编排，可按人员数量压缩。

## 3. 第 0 阶段：立项与需求冻结（第 1～2 周）

### 3.1 定义 MVP 边界

第一版必须有：

- 账号注册/登录与三类角色：学生、教师、管理员。
- 课程、班级、成员、章节。
- 资源上传与学生查看。
- 题库、试卷、考试、答卷、成绩。
- 学习进度、错题与基础学习统计。

第一版不必有：复杂多租户、直播、支付、多人实时协作、全自动判主观题、多模型编排。

### 3.2 需求产物

| 产物 | 内容 |
|---|---|
| PRD | 用户角色、业务范围、页面清单、非功能指标 |
| 用户故事 | 每项功能的操作者、目标、前置/异常条件、验收标准 |
| 权限矩阵 | 角色—页面—接口—数据范围四级关系 |
| 状态机 | 课程、资源、试卷、考试、答卷的状态变化 |
| 原型 | 教师端、学生端、管理端关键页面与字段 |
| 风险清单 | 考试并发、数据隐私、AI 成本、云服务依赖 |

### 3.3 最早确认的核心规则

- 一门课程由一个教师创建，可包含多个班级和章节。
- 学生只能访问已加入班级或公开课程的已发布内容。
- 试卷发布时保留题目快照，历史答卷不受题目后续编辑影响。
- 考试时长与提交以服务端时间为准。
- 错题、掌握度等均是可重算的学习视图，答卷是原始事实。

**阶段验收：** 每个核心用户故事都有可测试的验收标准，团队对“课程发布”“考试提交”等名词没有歧义。

## 4. 第 1 阶段：领域建模与总体架构（第 3～4 周）

### 4.1 划分领域与数据归属

| 领域 | 聚合/核心对象 | 数据唯一拥有服务 |
|---|---|---|
| 身份与组织 | User、Role、Permission、Dept | user |
| 教学组织 | Course、Class、ClassMember、Chapter、Section | course |
| 教学资源 | Resource、VideoMeta、ResourceBinding | resource |
| 测评 | Question、QuestionBank、Paper、Exam、Answer | exam |
| 知识图谱 | KnowledgePoint、KnowledgeRelation、QuestionKnowledge | knowledge |
| 学习行为 | LearningRecord、WrongRecord、Mastery | learning |
| 智能能力 | Document、Chunk、Embedding、ChatSession | ai |

### 4.2 决定同步和异步边界

同步（立即要结果）：登录、课程列表、学生是否属于班级、提交答卷的接收确认。

异步（允许最终一致）：课程发布通知、资源转码/解析、答卷后的错题和掌握度更新、知识关联清理、AI 文档向量化。

### 4.3 先定接口和事件契约

- 前端接口：REST + OpenAPI；请求 DTO、响应 DTO、错误码独立定义。
- 服务间查询：Feign 客户端 + `Intelli-Edu-api` 中的 DTO。
- 服务间事件：RabbitMQ；事件格式含 `eventId`、`eventType`、`aggregateId`、`occurredAt`、`operatorId`、`payloadVersion`。
- 任何服务都不能将数据库 Entity 作为外部 API 返回。

### 4.4 架构决策记录（ADR）

必须留下决策原因：选择 PostgreSQL、采用 Nacos、为何分出学习域和知识域、为何 AI 独立服务、何时使用 MQ、缓存失效策略。

**阶段验收：** 能画出“学生提交答卷后，考试、学习、知识服务如何交互”的时序图；每张表都能明确数据主人。

## 5. 第 2 阶段：工程与基础设施底座（第 5～6 周）

### 5.1 创建工程结构

```text
Intelli-Edu-backend/
├── Intelli-Edu-common/      # 通用异常、响应、日志、序列化、数据库配置
├── Intelli-Edu-api/         # DTO、Feign Client、fallback 接口
├── Intelli-Edu-auth/        # 鉴权 SDK
├── Intelli-Edu-gateway/     # 网关
├── Intelli-Edu-user/
├── Intelli-Edu-course/
├── Intelli-Edu-resource/
├── Intelli-Edu-exam/
├── Intelli-Edu-Knowledge/
├── Intelli-Edu-learning/
└── Intelli-Edu-Ai/
```

### 5.2 每个服务的标准分层

```text
controller/  接口、参数校验、协议转换
service/     用例编排和事务
model/       Entity、DTO、VO、枚举、命令
mapper/      MyBatis Mapper / SQL
config/      本服务配置
client/      服务间调用（或由 api 模块提供）
```

### 5.3 公共能力先完成

- 统一 `Result<T>`、业务异常和全局异常处理。
- 参数校验、分页、OpenAPI/Knife4j、时间序列化。
- `traceId`、操作日志、全局请求日志、敏感字段脱敏。
- MyBatis-Plus 分页、乐观锁、自动填充字段、逻辑删除约定。
- Redis 序列化、缓存 Key 规范、分布式锁封装。
- JWT 签发/解析、登录用户上下文、Feign 用户信息透传。
- Maven 父 POM、版本管理、统一构建插件。

### 5.4 本地环境一键化

通过 Docker Compose 同时创建：PostgreSQL + pgvector、Redis、RabbitMQ、Nacos、前端、网关和全部后端服务；初始化 Nacos 的共享配置与各服务配置，初始化空库结构。

当前项目本地编排入口：

```powershell
cd Intelli-Edu-backend/.hsunr/docker
docker compose up -d --build
```

**阶段验收：** 新成员不安装 Java/Maven/Node/数据库，按 README 能启动全栈；网关文档可见，全部服务注册 Nacos。

## 6. 第 3 阶段：用户、认证与系统管理（第 7～8 周）

### 6.1 数据模型

```text
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
   │
   └── sys_dept
```

用户重点字段：账号、昵称、密码哈希、邮箱/手机号、头像、用户类型、状态、院系、创建/更新时间。

### 6.2 功能开发顺序

1. 管理员初始化、用户 CRUD、院系管理。
2. 角色、菜单、接口权限绑定。
3. 注册、密码登录、验证码登录、验证码校验。
4. JWT access token / refresh token、退出登录、Token 失效与刷新。
5. 当前用户信息、个人资料、头像、修改密码。
6. 网关认证过滤器与服务内部用户上下文。
7. 登录日志、操作日志、失败登录限流。

### 6.3 验收用例

- 未登录访问 `/courses`、`/exams` 等受保护接口会被拒绝。
- 学生不可调用教师发布课程接口。
- 教师只能修改自己创建的课程和班级。
- 管理员能分配角色，但不能看到密码或 Token 明文。

**阶段成果：** 已有可被前端使用的登录、菜单、用户管理与权限基础，后续领域全部复用同一身份体系。

## 7. 第 4 阶段：课程、班级、章节（第 9～10 周）

### 7.1 数据模型与关系

```text
Category ──< Course ──< Class ──< ClassMember >── User
                     └──< Chapter ──< Section
```

### 7.2 功能开发顺序

1. 课程分类、课程创建和编辑。
2. 课程状态机：`DRAFT → PUBLISHED → ARCHIVED`。
3. 班级创建、班级码/邀请加入、学生成员管理。
4. 章节、课时、顺序调整。
5. 教师课程列表、学生课程列表、课程详情。
6. 课程发布后向班级学生发送事件/通知。

### 7.3 关键规则

- 课程/班级/章节写操作必须核验教师归属。
- 同一用户加入同一班级必须幂等，数据库有唯一约束。
- 已发布课程的公开字段可编辑；破坏性变更须明确通知策略。
- 章节排序使用排序字段和事务/乐观锁，避免并发拖动错乱。

**阶段成果：** 教师可完整搭建一门可发布的课程，学生能够看到自己所属课程和章节目录。

## 8. 第 5 阶段：资源中心与教学内容（第 11～12 周）

### 8.1 资源服务职责

- 文件元数据：名称、大小、MIME、哈希、上传者、存储 Key、状态、访问范围。
- 视频元数据：时长、封面、转码状态、播放地址。
- 通用资源与课程章节的绑定关系。
- 授权上传、授权下载、资源删除与审核。

### 8.2 开发流程

```text
前端申请上传凭证
→ resource 校验用户/文件类型/大小
→ 返回预签名上传地址
→ 客户端直传对象存储
→ 上传回调/确认
→ 资源状态变为 READY
→ course 绑定到章节
→ 学生鉴权后获取短时访问地址
```

### 8.3 关键规则

- 大文件不经业务服务转发。
- 存储服务可替换：开发可 mock，生产接 COS/VOD。
- 资源删除是状态变更与延迟物理清理，必须检查是否被课程/试卷/AI 文档引用。
- 视频转码、文件扫描、文档抽取使用异步任务。

**阶段成果：** 课程从“有目录”变成“学生真正能学习的内容”。

## 9. 第 6 阶段：知识点、题库、试卷与考试（第 13～16 周）

### 9.1 知识域

- 按课程维护知识点树，支持增删改查、层级与排序。
- 章节关联知识点，题目关联知识点。
- 知识域不拥有课程、题目本身，只保存外部 ID 与关联关系。
- 操作知识点前调用课程服务确认操作者是课程教师，或保存可验证的权限快照。

### 9.2 题库与组卷

```text
QuestionBank ──< Question >──< QuestionKnowledge >── KnowledgePoint
Paper ──< PaperQuestion（题目快照）
```

支持单选、多选、判断、填空、简答等题型；题目字段包含题干、选项、标准答案、解析、难度、分值、状态。

### 9.3 考试与答卷

```text
Paper → Exam → AnswerSheet → AnswerItem
```

开发顺序：

1. 题库、题目、知识点关联。
2. 手动选题组卷与试卷预览。
3. 试卷发布，冻结题目快照。
4. 考试创建：关联班级、开始结束时间、时长、次数、发布状态。
5. 学生获取考试和答卷草稿；定时保存。
6. 提交答卷，幂等处理；客观题即时判分。
7. 教师阅卷主观题、发布成绩、查看统计。

### 9.4 关键实现点

- 答卷唯一键：`exam_id + student_id`；提交接口以请求幂等键防止重复。
- 所有分数计算使用服务端规则；不能信任前端传回的总分。
- 考试与答卷都使用状态机；过期/强制交卷由服务端时间判断。
- 考试发布和答卷提交后分别发布事件，供通知与学习服务消费。

**阶段成果：** 平台具备可用的“教、练、考、评”闭环。

## 10. 第 7 阶段：学习记录、错题与掌握度（第 17～18 周）

### 10.1 学习服务输入与输出

输入：资源学习进度、章节完成、答卷提交、题目判分、考试结束事件。

输出：课程学习进度、章节完成率、错题本、知识点掌握度、教师班级学情统计、学生推荐数据。

### 10.2 建设方式

1. 定义学习事件并由课程/资源/考试服务发布。
2. `learning` 消费事件，记录原始学习事实并更新聚合视图。
3. 按“用户 + 题目”聚合错题，保留最近错误时间、次数和订正状态。
4. 按“用户 + 知识点”计算掌握度，初期可使用正确率/衰减公式，后续替换为更复杂模型。
5. 为学生提供进度、错题；为教师提供班级、题目、知识点统计。

### 10.3 可靠性要求

- 生产端采用 Transactional Outbox；事件与业务数据同事务落库。
- 消费端严格幂等，失败重试，超限进入死信队列。
- 学习统计最终一致；答卷和原始学习事件必须可追溯、可重放。

**阶段成果：** 平台不只保存“学生做了什么”，还能回答“学生哪里没掌握”。

---

## 11. 第 8 阶段：AI 助教与资料问答（第 19～20 周）

### 11.1 能力范围

- 课程资料上传后的文档解析、分块和向量化。
- 基于课程资料的检索增强问答（RAG）。
- AI 会话列表、会话历史和上下文控制。
- 可选的课程内容/题目辅助生成，但必须以人工审核为最终入口。

### 11.2 RAG 链路

```text
资料上传完成
→ 异步抽取 PDF/Word/Markdown 文本
→ 清洗、切块、记录课程与权限元数据
→ Embedding
→ 写入 pgvector/Redis Vector
→ 用户提问并按课程权限过滤检索
→ LLM 生成含资料来源的回答
```

### 11.3 必须具备的治理

- 模型密钥只来自 Secret/环境变量，绝不进入仓库。
- 每个用户与课程设置并发、频率、Token/费用配额。
- 模型超时、失败或无密钥时明确降级，绝不阻塞课程、考试等核心服务。
- 过滤未授权资料；回答显示引用来源；记录必要审计。

**阶段成果：** AI 能安全增强教学，而不会成为数据泄露或成本失控源。

---

## 12. 第 9 阶段：质量、可观测性和生产发布（第 21～24 周）

### 12.1 测试金字塔

| 测试 | 重点 |
|---|---|
| 单元测试 | 权限、状态机、判分、掌握度、幂等规则 |
| 集成测试 | Controller + PostgreSQL/Redis/RabbitMQ + Feign 契约 |
| 契约测试 | 前后端 OpenAPI、跨服务 DTO 兼容性 |
| E2E | 教师建课到学生完成考试的完整链路 |
| 压测 | 登录、课程列表、资源访问、考试提交 |
| 安全测试 | 越权、注入、文件上传、Token、依赖漏洞 |

### 12.2 可观测性

- 所有 HTTP、Feign、MQ 日志携带 traceId。
- Prometheus 指标：QPS、P95/P99、错误率、JVM、连接池、缓存命中、MQ 堆积、AI 成本。
- Grafana 看板和告警：服务不可用、5xx 激增、考试提交失败、数据库连接耗尽、死信堆积。
- 每个服务编写 Runbook：部署、扩容、回滚、排障、告警处理。

### 12.3 CI/CD

```text
代码提交
→ 格式与静态检查
→ 单元/集成测试
→ 依赖与密钥扫描
→ 构建 Maven 制品、Docker 镜像
→ 自动部署测试环境
→ 冒烟/E2E
→ 审批
→ 灰度发布生产
→ 指标验证
→ 全量或回滚
```

### 12.4 数据库与发布

- 所有 schema 变化使用 Flyway/Liquibase 版本迁移；已发布迁移不修改。
- 上线前在空库与已有数据升级库执行迁移演练。
- 生产有备份、恢复演练、镜像不可变标签和数据库回滚预案。

**阶段验收：** 可完成测试环境自动发布；可演练错误发布回滚；能够以 traceId 定位一条跨服务请求。

## 13. 全程统一的开发工作流

每一个需求都必须走完以下步骤：

```text
需求卡与验收标准
→ 领域/权限/状态机评审
→ API 和事件契约评审
→ 数据库迁移与索引设计
→ 后端实现（校验、鉴权、事务、幂等、审计）
→ 单元/集成测试
→ 前后端联调与 E2E
→ 指标、日志、告警
→ Code Review
→ 测试环境发布、验收、灰度生产
```

### Definition of Done

- [ ] 需求、角色权限、异常流程和验收条件明确。
- [ ] OpenAPI/Feign/MQ 事件契约已更新。
- [ ] 数据库迁移、索引、历史兼容和回滚方案已经评审。
- [ ] 完成参数校验、数据权限、事务、幂等、审计。
- [ ] 核心规则有单测，关键接口有集成测试，主链路有 E2E。
- [ ] 日志与指标已补齐；没有暴露密钥或隐私数据。
- [ ] 已通过代码评审并在测试环境验证。

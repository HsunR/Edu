# Intelli-Edu Frontend 大规模重构总览

## 一、项目现状诊断

### 1.1 核心架构问题

| # | 问题 | 严重程度 | 影响范围 |
|---|------|---------|---------|
| 1 | 双 Store 体系并存（`src/store/` + `src/stores/`），同名 ID 冲突 | 🔴 致命 | 全局 |
| 2 | API 层两套风格混用（旧式 `request({url,method})` + 新式 `request.post()`） | 🔴 严重 | 全局 |
| 3 | API 路径前缀不统一（`/user/auth/login` vs `/api/user/auth/login`） | 🔴 严重 | 全局 |
| 4 | JS/TS 混用，大量文件无类型安全 | 🟡 中等 | 全局 |
| 5 | 两套 UI 框架并存（Element Plus + Ant Design Vue） | 🟡 中等 | 构建/包体积 |
| 6 | 全局属性挂载（`globalProperties`）不符合 Vue 3 最佳实践 | 🟡 中等 | 全局 |
| 7 | 缺少 Composables 层，逻辑分散在组件中 | 🟡 中等 | 可维护性 |
| 8 | 类型系统不完善，大量 `any`、魔法数字、中文字面量 | 🟡 中等 | 类型安全 |
| 9 | 运行时错误风险（未导入函数、未定义变量、废弃 API） | 🔴 严重 | 稳定性 |
| 10 | Vite 代理配置不完整，旧版 API 请求无法代理 | 🟡 中等 | 开发体验 |

## 四、重构原则

1. **渐进式重构**：每个阶段独立可验证，不跨阶段依赖
2. **先删后建**：先删除废弃代码，再创建新代码
3. **类型先行**：先定义类型，再写实现
4. **测试验证**：每个阶段完成后手动验证核心流程（登录、课程浏览、考试）
5. **单一职责**：每个文件只做一件事
6. **Composition API**：统一使用 Composition API 风格
7. **全 TypeScript**：所有新代码和重写代码使用 TypeScript

## 六、风险控制

| 风险 | 应对措施 |
|------|---------|
| Store ID 冲突 | 先删除旧 Store，再创建新 Store |
| API 路径变更 | 在请求拦截器中统一添加 `/api` 前缀 |
| 组件重构影响页面 | 逐个组件重构，每次重构后验证 |
| 类型定义不完整 | 先用 `unknown` 替代 `any`，逐步完善 |
| Vite 代理不匹配 | 统一后端 API 前缀为 `/api` |
